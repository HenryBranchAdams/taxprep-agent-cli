# Case and rules integration contract

Schema version: `2.0`. Reference catalog year: `2025`. The evaluator validates supported case structure at runtime. This document describes that contract; it is not a JSON Schema validator file.

## Case root

Required fields are `schema_version`, `catalog_year`, `case_id`, `screens`, `entities`, `enumerated`, `evidence`, `reviews`, `form_decisions`, `route_decisions`, and `audit`. `created_at` is generated by the new-case function. Additional integration metadata is permitted but ignored by the evaluator unless explicitly supported.

`screens` must contain every optional catalog module. Its value is null or an answer record. Screen values must be boolean or unknown. Mandatory modules do not have optional screen answers.

`entities` must contain every module. Singleton modules contain exactly one entity with ID `return`. Repeatable modules contain zero or more separately identified entities. Each entity has `id`, `label`, `owner_ids`, and `answers`. IDs must be nonblank strings without `/`. Ownership must refer to valid PERSON instance IDs; missing/invalid ownership produces an open issue.

An answer is null or `{value, status, source, reference, at}`. `status` is `confirmed`, `tentative`, or `conflict`. Only confirmed records provide known predicate values. Values must match the question's declared type and enum choices. A confirmed null remains unknown.

`enumerated[module]` contains `{complete, entity_ids, at, source}`. The seal is valid only when `complete` is true and its sorted entity IDs match the current roster. An empty active repeatable roster cannot be declared complete.

## Predicates

Conditions may be literal true/false or objects:

```json
{"op":"all","args":[
  {"op":"eq","fact":"RETIRE.distribution","value":true},
  {"op":"eq","fact":"RETIRE.rollover","value":true}
]}
```

Supported operators: `eq`, `ne`, `in`, `gt`, `ge`, `lt`, `le`, `answered`, `all`, `any`, `not`. Predicate references are scoped to the current instance. Explicit singleton cross-module references can be used; raw repeated cross-instance references are prohibited because they require an aggregate adapter.

Unknown is a distinct value. False dominates an AND; true dominates an OR; otherwise unknown propagates. Inactive child facts yield false for leaf predicates, preventing stale child values from reactivating rules. Module screening precedes local predicate evaluation.

## Work item keys

- Question: `MODULE/instance/QUESTION_ID`
- Evidence: `MODULE/instance/evidence/DOCUMENT_ID`
- Form decision: `MODULE/instance/form/FORM_ID`
- Review: `MODULE/instance/RULE_ID/review`
- Route: `MODULE/instance/route.SOURCE.question.DESTINATION`

Task keys are stable links, not filenames. Never substitute a task from another instance because the form name is the same.

## Evidence record

```json
{
  "status":"verified",
  "fingerprint":"current evaluator-provided fingerprint",
  "reference":"secure file pointer + page/box/line",
  "actor":"named reviewer",
  "note":"what was matched and reconciled",
  "checks":{
    "year":true,"owner":true,"entity":true,
    "complete":true,"corrections":true,"reconciled":true
  },
  "at":"ISO timestamp"
}
```

Allowed catalog states: missing, searching, located, verified, rejected, alternative_accepted, not_required, stale. Closed support is verified, alternative_accepted or not_required. Verified/alternative_accepted records need all six checks, a reference, actor, note and matching fingerprint. Not_required needs a reference, actor, rationale and matching fingerprint but does not falsely assert a verified source file exists. Missing closure fields keep the item open.

The prototype does not authenticate a reviewer or determine whether their substantive conclusion is correct. A production adapter must enforce authorization, roles, data retention and review policies separately.

## Decision records

Form decisions use `{decision: required | not_required, fingerprint, actor, reference, note, at}`. Until a valid reviewed decision exists, the form remains a candidate. Technical/route resolutions use `{status: resolved, fingerprint, actor, reference, note, at}`. Route references should identify the downstream instance(s) or a documented nonapplicability conclusion.

`fingerprint` is generated by the evaluator. Never invent it or reuse one blindly across instances. It is a content-based FNV-1a invalidation marker, not a cryptographic signature. A changed fact context makes matching closed records stale. Identical restored context can match the previous record again. Changing source bytes without changing facts is not detected automatically; a production source-version integration must handle that explicitly.

## Report contract

`evaluate(case)` returns `screens`, `modules`, `questions`, `evidence`, `form_candidates`, `reviews`, `routes`, `issues`, `summary`, `inactive_evidence_preserved`, `authorization` and `readiness`, together with case/year identification.

Readiness is `OPEN` until every modeled blocker is cleared, or `READY_FOR_PREPARER_REVIEW` when all are cleared. No state means ready to file or a correct tax calculation. Unsupported years and nonindividual scope are hard issues; negative completeness answers also remain issues rather than counting as completion merely because they were answered.

`agent_plan.build_plan(case)` joins this report to the support specifications and produces explicit next actions, search terms/locations, required fields, acceptance criteria, candidate-form assembly rules and review responsibilities. The plan performs no external actions.

## Extension/adapters

Use a versioned extension when a jurisdiction, specialist fact pattern or aggregate computation is not fully implemented. Its contract should identify: tax year, jurisdiction, supported facts/conditions, authoritative versions, required question IDs, source/evidence specs, calculation assumptions, output obligations, deadlines, unresolved cases, tests and reviewer disposition.

Do not close the parent review by merely naming a specialist. Attach the resulting decision/evidence record or leave it open. Additional extension fields can live in case metadata, but the base evaluator does not execute them; integration requires either additional catalog rules with tests or a validated externally completed handoff.
